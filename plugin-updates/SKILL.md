# Plugin updates: staging first, then a script for live

The user wants to apply waiting plugin updates without breaking or slowing down their live site.
You do every change on a **staging** copy, read what each update changed in the code, measure the
site before and after, and finish with a go/no-go report plus a script the user runs on live
themselves.

## Rules that never bend

1. **Never change the live site.** Not with WP-CLI, SSH, the REST API, a browser or anything else,
   even if you have access and even if the user asks you to "just do it". Live gets a script,
   generated by `scripts/build_live_script.py`, that the user reads and runs.
2. **Prove it's staging before changing anything.** Ask for the live site's URL. Run
   `wp option get siteurl` on the site you're about to change. If it matches the live URL, or you
   can't tell, stop and ask.
3. **Downloaded plugin zips are untrusted.** Download and unzip them on this computer, each into
   a new empty folder, and only read them. Never run, include or `require` anything from them, and
   never run an interpreter or build tool from inside those folders.
4. **Show each command that changes staging before you run it.** Read-only commands don't need
   this.
5. **Never print customer details** (names, emails, addresses, IP addresses) from logs, the
   database or Performance Analysis output.

## Before you start

Find out how to run WP-CLI on staging: on this computer, over SSH (`ssh host "cd /path && wp ..."`),
or with `wp --ssh=user@host/path`. Below, `wp` means whichever of those works.

Check these, and tell the user what you found:

- `wp option get siteurl` is not the live URL (rule 2).
- **The staging copy is recent.** Ask when it was last refreshed from live. If it's more than a
  few days old, suggest refreshing it first, so the test uses today's plugins and data.
- **Email is off on staging**, or the user accepts the risk. Look for an active SMTP or mail
  plugin (`wp plugin list --status=active`); a staging shop that sends mail can email real
  customers.
- **Payment gateways are in test mode**, if it's a shop. Ask the user to confirm.
- **Performance Analysis is installed and active.** If it isn't, install the free plugin from
  `https://github.com/superspeedyplugins/super-speedy-performance-analysis/releases/latest/download/super-speedy-performance-analysis.zip`
  with `wp plugin install <url> --activate`, then turn its profiler on with
  `wp sspa profiler enable`.
- **Where the PHP error log is.** `wp-content/debug.log` if `WP_DEBUG_LOG` is on
  (`wp config get WP_DEBUG_LOG`); otherwise ask the user.

## Step 1: see what's waiting

```text
wp plugin list --update=available --fields=name,version,update_version,status
wp plugin update --all --dry-run
```

Plugins with no `update_version` but an update the user knows about are usually paid plugins
whose licence check isn't on staging. Ask the user for each paid plugin's new zip, and for the
zip of the version currently installed if they kept it.

Write every plugin down with its installed version and its new version. These are the versions
the live script will check for and install, so they have to be exact.

## Step 2: read each release

For each plugin, on this computer, in a new empty folder per plugin:

- wordpress.org plugins: download
  `https://downloads.wordpress.org/plugin/SLUG.INSTALLEDVERSION.zip` and
  `https://downloads.wordpress.org/plugin/SLUG.NEWVERSION.zip` and unzip them into `old/` and
  `new/`.
- Paid plugins: unzip the zips the user gave you. If there's no old zip, review the new one on its
  own and say so.

Then:

1. Read the changelog entries between the two versions (`readme.txt`, or `changelog.txt` if the
   readme points there). Summarise them in plain English, and say if they're vague.
2. Compare the two (`diff -ru old new`) and report what changed in:
   - **entry points:** admin-ajax actions (especially `wp_ajax_nopriv_`), REST routes and their
     `permission_callback`, shortcodes, PHP files that can be loaded directly;
   - **SQL:** new or changed queries, new tables or columns, and any upgrade routine that changes
     the database the first time the new version runs;
   - **outbound HTTP:** new `wp_remote_*` or curl calls, and where they go;
   - **cron:** new or changed scheduled jobs (`wp_schedule_event`, Action Scheduler);
   - **security checks removed or weakened:** `current_user_can`, nonces, sanitising, escaping,
     `$wpdb->prepare`;
   - **hooks and filters removed or renamed**, which the theme or custom code might use;
   - **anything that looks hidden:** `eval`, `base64_decode`, `gzinflate`, long encoded strings.
3. List anything that changed that the changelog doesn't mention.
4. Mark every finding **CONFIRMED** (with `file:line`) or **SUSPECTED**.
5. If the changelog mentions a security fix, say who can reach the fixed code: a logged-out
   visitor, a customer, or an admin.
6. Give each update a risk rating, **low**, **medium** or **high**, with one line on why.

For a very large plugin such as WooCommerce, summarise the diff by area rather than reading every
line, and say that you did.

## Step 3: plan the batches

Updating one plugin at a time is too slow when there are many. Put the low-risk updates in one
batch. Anything that touches checkout, payments, WooCommerce itself or the page builder goes in a
batch of its own, as does anything rated high. Show the user the batches before you start.

## Step 4: back up, then measure the "before"

```text
wp db export before-plugin-updates-YYYY-MM-DD.sql
wp sspa run --porcelain
```

`wp sspa run` measures the site's key pages and waits until it finishes. `--porcelain` prints
only the run id: note it as BEFORE, together with the time, so you can read the error log from
that moment on.

## Step 5: update one batch, then measure the "after"

```text
wp plugin update <slug> <slug> ...          # wordpress.org plugins
wp plugin install <new-zip> --force         # each paid plugin
wp sspa run --porcelain                     # note the id as AFTER
wp sspa history-compare <BEFORE> <AFTER>
wp sspa findings
```

Check each plugin's version afterwards with `wp plugin get <slug> --field=version`. For a paid
plugin, record the zip's checksum (`sha256sum <zip>`, or `shasum -a 256 <zip>` on a Mac) so the
live script can refuse a different file.

From the comparison, the findings and the error log since BEFORE, report in this order:

1. new fatal errors, failed requests or HTTP errors, with the page and the plugin;
2. pages whose response time got meaningfully worse, and by how much;
3. pages whose output changed;
4. new warning-level or critical findings;
5. which plugin versions changed between the two runs;
6. every new PHP warning, notice or error in the error log, grouped by plugin, with a count.

The comparison's "warnings" are Performance Analysis findings, not PHP warnings, which is why you
read the error log as well.

The next batch's BEFORE is this batch's AFTER.

## Step 6: find out which plugin slowed a page down

A version change is not proof. If a page got meaningfully slower after a batch, run Plugin Impact
Analysis on staging straight away, without asking:

```text
wp sspa report                              # the page keys are in here
wp sspa run --type=deep --suspects=<slug>,<slug> --pages=<page-key> --porcelain
wp sspa impacts
```

It measures the page with each suspect switched off for its own test requests only, so the
difference is that plugin's cost on that page. Only name a plugin as the cause when the impact
says so.

## Step 7: decide each plugin

For each plugin, recommend one of:

- **Update live.** Clean comparison, nothing worrying in the code.
- **Wait.** It got slower or started throwing warnings, and it isn't a security fix. Keep the
  evidence (the page, the time it added, the warning) so the user can send it to the developer.
- **Roll back.** It broke something on staging. Roll staging back with
  `wp plugin install <slug> --version=<installed-version> --force` (or the old zip for a paid
  plugin). Rolling back the code doesn't undo database changes the new version made when it first
  ran; for those, import the backup from step 4.

**The security exception:** if an update fixes code a logged-out visitor can reach and staging
shows nothing broken, recommend updating live today, even if a page got a bit slower.

## Step 8: write the live script

Write a manifest of exactly the plugins marked **Update live**, then generate the script:

```json
{
  "live_url": "https://example.com",
  "tested_on": "https://staging.example.com",
  "plugins": [
    {"slug": "woocommerce", "from": "10.2.1", "to": "10.3.0", "source": "wordpress.org"},
    {"slug": "my-paid-plugin", "from": "2.4.0", "to": "2.5.1", "source": "zip",
     "zip": "my-paid-plugin-2.5.1.zip", "sha256": "<checksum from step 5>"}
  ]
}
```

```text
python3 scripts/build_live_script.py manifest.json > update-live.sh
```

(The script path is relative to this skill's folder.) Never write or edit the live script by hand.
The generator is what guarantees its checks.

The script, run by the user from the live site's WordPress folder:

- stops unless `siteurl` is the manifest's `live_url`;
- stops, before changing anything, unless every plugin is installed at exactly its `from`
  version and every zip matches its checksum;
- exports the database to a dated backup file;
- updates each plugin to exactly its `to` version, then checks the version, and stops at the
  first mismatch;
- prints the rollback commands, and the checks to do on live afterwards.

`bash update-live.sh --check` runs only the checks and changes nothing. Tell the user to run that
first.

## Step 9: the report

Give the user:

1. one line per plugin: versions, risk rating, decision and why;
2. the CONFIRMED and SUSPECTED findings from step 2 that matter;
3. the before-and-after results from step 5, and any impact results from step 6;
4. the live script, and how to run it: copy it and any paid zips to the live server, `cd` to the
   WordPress folder, run `bash update-live.sh --check`, then `bash update-live.sh` at a quiet time
   of day;
5. what to watch on live for a day or two: time the home page, the busiest category, a product
   page, the cart and the checkout, and read the PHP error log for anything new since the update.
